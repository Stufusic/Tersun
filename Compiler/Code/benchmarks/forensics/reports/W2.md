# G6R.1 Workload Forensic Dossier: W2 (Sieve)

## 1. Workload Definition
- **Name**: Prime Sieve of Eratosthenes ($N=100,000$)
- **Algorithm**: Đánh dấu các bội số của số nguyên tố trong mảng kích thước $100k$.
- **Source**: `benchmarks/forensics/inputs/w2_sieve.stn`
- **Tập trung điều tra**: Mảng số nguyên/boolean, FlatArray I64 vs Generic Boxed, bounds checking overhead, boxing/unboxing leak.

## 2. Expected Behavior
- Mảng boolean/integer $100,000$ phần tử.
- Hàng trăm nghìn thao tác đọc và ghi phần tử mảng trong vòng lặp lồng nhau.
- Rất nhạy cảm với cơ chế đại diện bộ nhớ (representation) và kiểm tra biên mảng (bounds check).

## 3. Benchmark Baseline
- Input Checksum: `9592` số nguyên tố tìm được dưới 100k.
- Môi trường: Windows 11 x64, Intel Core i5-1245U, GCC 15.2.0 C++20.

## 4. Cold Results
- Cold Process Wall-Clock: **86.16 ms**
- Internal Cold Execution Time: **71.39 ms**
- Startup/Teardown Delta: **14.77 ms**

| :--- | :--- | :--- | :--- | :--- |
| **$M0$ (Switch Interpreter)** | 72.18 ms | 81.88 ms | 6.80% | 1.00x (Baseline) |

| **$M2$ (Baseline JIT)** | 15.40 ms | 21.75 ms | 17.29% | 4.69x |

## 6. Opcode Profile
- Total Superinstructions Executed ($M1$): $4,209,997$
- Tần suất các opcode thao tác mảng `ARRAY_GET`, `ARRAY_SET` chiếm áp đảo.

## 7. Tier Profile
- JIT ($M2/M3$) giảm thời gian từ 72.18 ms xuống 14.93 ms ($\sim 4.8\times$ speedup).
- Native AOT ($M4$) đạt 2.06 ms nhờ memory stride optimization và triệt tiêu toàn bộ bounds check.

## 8. Memory / GC Profile
- Cấp phát ban đầu: 1 buffer mảng $100k$ phần tử.
- 0 heap allocation trong vòng lặp sàng lọc chính.
- GC pause: 0 ns.

## 9. Specialization Profile
- FlatArray I64 đảm bảo không bị boxing leak.
- Tuy nhiên mọi thao tác truy cập đều phải trải qua runtime bounds check.

## 10. A/B Experiments
- **$E4$ (FlatArray)**: Đã chứng minh FlatArray ngăn chặn việc tạo đối tượng đa hình boxed `VMValue` cho từng số nguyên.

## 11. Suspects
- Suspect 1 (R4): Generic Array representation leak.
- Suspect 2 (R4-B): Bounds check runtime tax.
- Suspect 3 (R1): Dispatch loop overhead.

## 12. Confirmed Root Cause
- **PRIMARY ROOT CAUSE**: Runtime Bounds Checking trong vòng lặp bước nhảy $j += i$. Mỗi lần gán phần tử đều kiểm tra $j < \text{len}$ dẫn đến branch prediction overhead.
- **SECONDARY CAUSE**: Thiếu Loop Unrolling trong JIT so với GCC/LLVM -O3.

## 13. Rejected Hypotheses
- **REJECTED**: GC pressure (mảng cấp phát một lần duy nhất).
- **REJECTED**: Field IC (không sử dụng struct/object).

## 14. Recommended Fix for G6R.2
1. Triển khai **Bounds Check Hoisting / Elimination (BCE)**: chứng minh vòng lặp $j < \text{length}$ là an toàn và bỏ qua kiểm tra biên trong thân vòng lặp.
2. Áp dụng Memory Stride Prefetching trong Tier-2 JIT.

## 15. Expected Metric Movement
- `bounds_check_count` $\downarrow$ 85%.
- JIT Execution time $\downarrow$ từ 14.93 ms xuống $< 4.0$ ms.
